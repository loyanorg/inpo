# Local-first development with an in-process database and the same SQL in production

**What it is:** tests and local dev run PostgreSQL in-process (PGlite, WASM); production runs real PostgreSQL; the SQL and migrations are identical.

## Take

- One database adapter interface with two implementations: `pglite` (in-process, in-memory or on disk) and `pg` (network). Selection by a single env var (`DATABASE_URL` empty or `memory://` selects PGlite).
- Migrations are plain SQL files, applied by the same migrator against both. CI runs the full migration set on PGlite on every push and on a real PostgreSQL container nightly or on release.
- `pnpm test` (or equivalent) needs no Docker, no running service, and finishes the engine suite in under 30 seconds. A fresh clone can run tests with install alone.
- Each test file gets its own PGlite instance, so tests run in parallel without shared state.
- Only SQL supported by both is allowed; a lint or CI step fails on extensions PGlite does not ship (check the PGlite extension list before adding one).
- Seed data for local dev is generated by the engine's own commands, not by inserting rows directly, so it always satisfies the rules.
- Demo or seed data is for exercising the UI; it is never a source of requirements (see Rejected list).

## Leave

- Running SQLite locally and PostgreSQL in production; dialect drift causes bugs that only appear after deploy.
- Mocking the repository layer in engine tests; the real SQL is cheap enough to run.
